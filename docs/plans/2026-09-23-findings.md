### core-logic:panel-hosted-autosync

**Move auto-sync out of the background and into the panel itself** — structure, severity medium, effort L, verdict partially, bold

- Evidence: The event-page machinery exists only because the tab listeners live in the background: unconditional top-level registration, the in-memory autoSyncEnabled cache, refreshAutoSyncEnabled, permission/storage listeners, tabEventSeq (background.ts:125-280, ~155 lines; docs/notes/permissions-model.md § event-page-wakeup; tests/background-module.test.ts 480 lines). The indirection causes: (a) resolution while the panel is closed (previous finding); (b) cross-window bleed (multi-window finding); (c) lost resolution method, because the background sends only {orgnr, host} and the panel stamps 'sync-broadcast' (details.ts:618-623), which hides 'Feil bedrift?' for exactly the host-auto guesses auto-sync produces; (d) a second resolver: the background uses the AUTO-only path (tab-sync.ts -> orgnr.ts:118-127 -> searchByHostname) and the panel re-runs the picker-aware pipeline on every no-match (details.ts:655-681), so a cold host runs the pipeline twice. Existence is encoded implicitly too: host-pick vs host-auto is inferred from candidates.length === 0 (resolve-tab.ts:66-67, details.ts:674-675). Why auto-sync was placed in the background is not documented anywhere I read.
- Recommendation: The panel (details.ts) registers tabs.onActivated/onUpdated while open, filters to its own window (browser.windows.getCurrent()), and calls the same resolveTabContext it uses at init. That keeps the method, shows the picker directly, and needs no messages. The panel document is alive exactly while it is visible, so there is no wake-up problem. The background shrinks to the context-menu handler; its one remaining message goes through a typed src/lib/messages.ts (union + guards) and carries windowId. Deletable: background.ts auto-sync half, tab-sync.deriveSyncAsync, orgnr.resolveOrgnrAsync, hostname-search.searchByHostname, the no-match re-resolve, and most of background-module.test.ts. Add an explicit `source: 'choice'|'pipeline'` field instead of the candidates.length trick. Verify panel-hosted tabs listeners on both engines before committing (not runtime-tested here).
- Verifier correction: The core holds: background-hosted auto-sync resolves while the panel is closed, loses the resolution method (hiding 'Feil bedrift?' for host-auto results), and is what causes the window bleed. But the panel re-runs the hostname pipeline only after an incomplete background run. Complete runs are cached in the shared storage.session, so the panel hits the cache. The menu handler's async path also depends on deriveSyncAsync, so it must be reworked before resolveOrgnrAsync and searchByHostname can be deleted.

### core-logic:cache-write-failure-is-fatal

**A failed cache write turns a successful fetch into an error, and expired entries are never swept** — risk, severity low, effort S, verdict confirmed

- Evidence: brreg.ts:53, 117, 127, 161, 199, 206, 217 and hostname-search.ts:270, 284 all `await cacheSet(...)` before returning, and session-cache.ts:37-43 does not catch. A quota or storage error therefore rejects fetchEnhet after the data arrived, and the UI shows an error. Expired entries are removed only when read (session-cache.ts:24-33). Payload sizes measured live: underenheter for 947054600 is 107 KB, 984851006 is 94 KB (up to about 160 KB at the size=100 cap). Chrome documents storage.session QUOTA_BYTES as 10 MB. The Firefox limit is unknown.
- Recommendation: Make cacheSet best-effort (try/catch, never throw), and make cacheGet treat a storage error as a miss. Optionally sweep expired keys opportunistically in cacheSet (get(null) and remove expired), and cache only the fields the UI renders for underenheter/search hits.

### ui-code:dishonest-soft-fail-roller-underenheter
